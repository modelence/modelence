This page is written for a coding agent. It describes what Modelence Cloud runs, the
`modelence.config.json` file that tells it how, and the steps to set up an existing project: a
Node.js app, or an app in any other language that builds with its own Dockerfile. If you are a
person, hand it to your agent:

```text
Use https://docs.modelence.com/deploy/setup.md to set up Modelence deployment for this project
```

## What Modelence Cloud runs

- **A Docker image built from the repository**, in one of two ways:
  - **A Node.js app** is built on an official Node.js image, 18 or newer (default `node-22-slim`,
    set with `image`). The `build` commands run in order in the resource's root; only npm is
    preinstalled.
  - **Any other app**, such as Python, Go, Ruby, Java, PHP or .NET, is built from the project's
    own Dockerfile, set with `dockerfile`. So is a Node.js app that needs system packages, such as
    ffmpeg. See [Projects with a Dockerfile](#projects-with-a-dockerfile).
- **One process**, started with the resource's `start` commands. The last one must keep running.
  A web process listens on the port in the `PORT` environment variable; a hardcoded port never
  receives traffic. A process that serves no traffic, such as a queue worker or a bot, sets
  `"healthCheck": "none"` and needs no port.
- **Optional static directories** (the resource's `static`) served in front of that process by the platform.
  Requests that match no file fall back to the directory's `index.html`, so single-page apps route on
  the client.
- **Optional managed PostgreSQL databases and Redis caches**, declared in `resources` next to the
  service. A deploy creates each one in the environment's region, and the app gets its connection
  details through the variables `env` ties to it. They need a paid Modelence Cloud plan.
- **Optional telemetry**, a `resources` entry of type `"telemetry"`. It gives the environment a
  private OpenTelemetry endpoint for the app's traces and metrics, kept for 30 days and shown on the
  environment's **Monitoring** page. It needs a Modelence Cloud plan with monitoring (Pro and up).
  Logs need no setup: the app's output is collected and shown on the **Logs** page.
- **Environment variables injected at start:**
  - `MONGODB_URI` and `MONGO_URL` — a MongoDB Atlas database provisioned for this environment
    (both hold the same connection string).
  - `SITE_URL` and `ROOT_URL` — the environment's public URL (both hold the same value).
  - `PORT` — the port the web process must listen on.
  - Any variables the user defines in the dashboard under **Environment variables**.
  - The variables `env` ties to a managed resource, such as `DATABASE_URL` from a PostgreSQL
    database's `url`, or `OTEL_EXPORTER_OTLP_ENDPOINT` from telemetry's `endpoint`.

  Names starting with `MODELENCE_`, and `PORT`, are reserved and cannot be defined by the user.

## modelence.config.json reference

`modelence.config.json` sits at the project root and is the whole contract between the project and
Modelence Cloud. Comments (`//`, `/* */`) and trailing commas are allowed. Apart from a resource's
`type`, every key is optional; a missing key takes the default.

The file has two top-level sections: `resources` (what the app is made of) and `env` (the variables
it expects).

| Key | Type | Default | Meaning |
| --- | --- | --- | --- |
| `$schema` | string | — | Set to `https://cloud.modelence.com/schema/modelence.config.json?version=1` for editor validation and completion. `version` is the format version the file is written for. |
| `resources` | object | `{}` | Everything the app is made of, keyed by a name you choose (`"api"`, `"main-db"`): the service, and any managed databases, caches and telemetry. Exactly one service is supported today. |
| `env` | object | `{}` | The variables the app expects, keyed by name. See below. |

A service entry of `resources` takes:

| Key | Type | Default | Meaning |
| --- | --- | --- | --- |
| `type` | `"service"` | required | What the resource is. `"service"` is a process built from this repository: a Node.js app, or an app in any language with a `dockerfile`. |
| `image` | string | `"node-22-slim"` | Base image, `node-<version>-<variant>`: a Node.js major (`"node-22-slim"`) or exact version (`"node-22.23.1-alpine"`), `18` or newer. `slim` is glibc and works with prebuilt native binaries; `alpine` is smaller. |
| `root` | string | `"."` | Subdirectory that holds the app, relative to the repository root (monorepos). Commands run there, and `static` directories are relative to it. |
| `build.commands` | string[] | `["npm install"]` | Commands that install dependencies and build the app, run in order. `[]` means there is no build step. |
| `start.commands` | string[] | none | Commands that start the web process, run in order; the last one must keep running. Omit `start` when there is no process: the site is static only and `static` must be set. |
| `dev.commands` | string[] | the package.json `dev` script in `root` | Commands `modelence dev` runs locally in `root`, in order, with the connected environment's variables; the last one must keep running. Never used by a deploy. |
| `static` | `[{ path, dir }]` | `[]` | Directories to serve. `path` is an absolute URL prefix (`"/"`, `"/docs"`); `dir` is relative to `root` and must exist after the build. |
| `dockerfile` | string | none | Build the service from this Dockerfile instead of `image` and `build`. The path is relative to `root`, and `root` is the build context. `image`, `build` and `static` can't be set with it, and `start` is required. See [Projects with a Dockerfile](#projects-with-a-dockerfile). |
| `healthCheck` | `"tcp"` \| `"none"` | `"tcp"` | How the platform tells that a container is healthy. `"tcp"`: something accepts connections on `PORT`. `"none"`: healthy once it runs, for a process that serves no traffic (a queue worker, a bot holding a gateway connection). |
| `rollout` | `"overlap"` \| `"replace"` | `"overlap"` | How a deploy replaces running containers. `"overlap"`: the new containers start, and the old ones stop once the new ones are healthy. There is no gap, but both versions run for a while. `"replace"`: the old containers stop before the new ones start, at the cost of a short gap. Use it for a process that must never run twice, such as a bot that allows one connection. |
| `stopTimeout` | number | `30` | Seconds a stopping container gets between `SIGTERM` and `SIGKILL` to finish its work, from 2 to 120. It stops receiving new traffic when `SIGTERM` is sent. |

A managed resource entry of `resources` takes:

| Key | Type | Default | Meaning |
| --- | --- | --- | --- |
| `type` | `"postgres"` \| `"redis"` \| `"telemetry"` | required | `"postgres"` is a PostgreSQL database, `"redis"` a Redis cache, `"telemetry"` the environment's OpenTelemetry endpoint. |
| `plan` | string | the smallest | The size to create it with. PostgreSQL: `postgres-1gb`, `postgres-2gb`, `postgres-4gb`, `postgres-8gb`, `postgres-16gb` (the RAM of the database). Redis: `redis-250mb`, `redis-1gb`, `redis-5gb` (the data it holds). Telemetry takes no `plan`. |

A deploy creates every managed resource the file declares that the environment doesn't have yet, and
the new version starts only once they are ready. Resources are matched by name, so the same file works
in every environment:

- A resource that already exists is kept as it is, with its data. `plan` is read only when the resource
  is created, so changing it later has no effect.
- A resource removed from the file is not deleted. Delete it in the dashboard under **Resources** when
  it is no longer needed; a database or cache is billed until then.
- Renaming a resource creates a new, empty one. The old one stays until it is deleted.

An environment can have up to 10 managed resources, telemetry included, and at most one of them can be
telemetry.

Each entry of `env` declares one variable:

| Key | Type | Default | Meaning |
| --- | --- | --- | --- |
| `type` | `"text"` \| `"secret"` \| `"resource"` | `"text"` | `"secret"` is write-only in the dashboard and revealed one value at a time. `"resource"` takes the value from a managed resource; see below. |
| `scopes` | (`"build"` \| `"runtime"`)[] | `["runtime"]` | Which phases the variable reaches. `"runtime"` is the running app; `"build"` is the build commands — needed for anything a bundler inlines, such as Vite's `VITE_*`. A value scoped to `["build"]` alone never reaches the running app. |
| `value` | string | — | A non-secret literal committed with the repository (a base path, a public API URL). Omit it to declare only the name: the dashboard then lists the variable and the user sets it per environment. A `"secret"` may never carry a value. |
| `required` | boolean | `true` | Whether the app needs a value to run. A deploy asks for every required variable that has no value, and a CI deploy fails without one. Set `false` for a variable the app runs without (an optional integration's key). |

A value set in the dashboard overrides a `value` written here, so a literal in the file is the
committed default rather than a fixed constant.

A variable with `"type": "resource"` takes its value from one output of a managed resource in the same
file, and takes only these keys:

| Key | Type | Meaning |
| --- | --- | --- |
| `type` | `"resource"` | Required. |
| `resource` | string | The name of a `postgres`, `redis` or `telemetry` entry in `resources`. |
| `output` | string | Which value of the resource. PostgreSQL: `url`, `host`, `port`, `user`, `password`, `database`. Redis: `url`, `host`, `port`, `password`. Telemetry: `endpoint`, `headers`. |

The `url` output is a full connection string: `postgresql://...?sslmode=require` for PostgreSQL and
`rediss://...` (TLS) for Redis. The other outputs are its parts, for clients that read them separately,
such as `PGHOST` and `PGPASSWORD`. These variables reach the running app only, not the build commands.
They can't be set or changed in the dashboard, where they are listed with the resource they come from.

Telemetry's outputs are the values of the standard OpenTelemetry variables:
`endpoint` for `OTEL_EXPORTER_OTLP_ENDPOINT` and `headers` for `OTEL_EXPORTER_OTLP_HEADERS`, which
holds the environment's credentials. The endpoint takes OTLP over HTTP and is private: only the
running app reaches it, not the build or a local machine.

<Note>
Apps built on the Modelence framework need no file: `npx modelence@latest deploy` recognizes the
`modelence` dependency and keeps building them locally, as it always has. To build one on Modelence Cloud
instead, describe it like any other Node.js app: `"build": { "commands": ["npm ci", "npm run build"] }`
and `"start": { "commands": ["npm start"] }`.
</Note>

**Missing, empty and none**: a missing `build` runs `npm install`; `"build": { "commands": [] }` means
there is no build step. A missing `start` means there is no process. An empty command string `""` is
invalid and is rejected.

## Examples

**Express API only** — no build step, the server serves everything:

```json modelence.config.json
{
  "$schema": "https://cloud.modelence.com/schema/modelence.config.json?version=1",
  "resources": {
    "api": {
      "type": "service",
      "image": "node-22-slim",
      "build": { "commands": ["npm ci"] },
      "start": { "commands": ["node server.js"] }
    }
  }
}
```

**Vite static site** — built once, served by the platform, no process:

```json modelence.config.json
{
  "$schema": "https://cloud.modelence.com/schema/modelence.config.json?version=1",
  "resources": {
    "web": {
      "type": "service",
      "image": "node-22-slim",
      "build": { "commands": ["npm ci", "npm run build"] },
      "static": [{ "path": "/", "dir": "dist" }]
    }
  }
}
```

**Express API + Vite frontend** — the frontend in `client/` is built into `client/dist` and served at
`/`; requests that match no file reach the API. `VITE_API_URL` is scoped to the build as well because
Vite inlines it while building:

```json modelence.config.json
{
  "$schema": "https://cloud.modelence.com/schema/modelence.config.json?version=1",
  "resources": {
    "api": {
      "type": "service",
      "image": "node-22-slim",
      "build": {
        "commands": ["npm ci", "npm ci --prefix client", "npm run build --prefix client"]
      },
      "start": { "commands": ["node server.js"] },
      "static": [{ "path": "/", "dir": "client/dist" }]
    }
  },
  "env": {
    "VITE_API_URL": { "value": "/api", "scopes": ["build", "runtime"] },
    "STRIPE_SECRET_KEY": { "type": "secret" }
  }
}
```

**Express API with PostgreSQL and Redis** - the deploy creates the database and the cache, and the
app reads them from `DATABASE_URL` and `REDIS_URL`:

```json modelence.config.json
{
  "$schema": "https://cloud.modelence.com/schema/modelence.config.json?version=1",
  "resources": {
    "api": {
      "type": "service",
      "image": "node-22-slim",
      "build": { "commands": ["npm ci"] },
      "start": { "commands": ["node server.js"] }
    },
    "main-db": { "type": "postgres", "plan": "postgres-1gb" },
    "cache": { "type": "redis" }
  },
  "env": {
    "DATABASE_URL": { "type": "resource", "resource": "main-db", "output": "url" },
    "REDIS_URL": { "type": "resource", "resource": "cache", "output": "url" }
  }
}
```

**Express API with telemetry** - the OpenTelemetry SDK reads the two variables, so requests and
database calls reach the environment without code changes. Logs are already collected from the app's
output, so `OTEL_LOGS_EXPORTER` turns off the SDK's own log export. The project depends on
`@opentelemetry/auto-instrumentations-node`, which `--require` loads before the server:

```json modelence.config.json
{
  "$schema": "https://cloud.modelence.com/schema/modelence.config.json?version=1",
  "resources": {
    "api": {
      "type": "service",
      "image": "node-22-slim",
      "build": { "commands": ["npm ci"] },
      "start": {
        "commands": ["node --require @opentelemetry/auto-instrumentations-node/register server.js"]
      }
    },
    "otel": { "type": "telemetry" }
  },
  "env": {
    "OTEL_EXPORTER_OTLP_ENDPOINT": { "type": "resource", "resource": "otel", "output": "endpoint" },
    "OTEL_EXPORTER_OTLP_HEADERS": { "type": "resource", "resource": "otel", "output": "headers" },
    "OTEL_SERVICE_NAME": { "value": "api" },
    "OTEL_LOGS_EXPORTER": { "value": "none" }
  }
}
```

**Python web app with a Dockerfile** - the image is built from the project's `Dockerfile`, and
`start` replaces its `CMD`. The server listens on `0.0.0.0` and the port in `PORT`:

```json modelence.config.json
{
  "$schema": "https://cloud.modelence.com/schema/modelence.config.json?version=1",
  "resources": {
    "api": {
      "type": "service",
      "dockerfile": "Dockerfile",
      "start": { "commands": ["uvicorn app.main:app --host 0.0.0.0 --port $PORT"] }
    },
    "main-db": { "type": "postgres" }
  },
  "env": {
    "DATABASE_URL": { "type": "resource", "resource": "main-db", "output": "url" },
    "OPENAI_API_KEY": { "type": "secret" }
  }
}
```

```dockerfile Dockerfile
FROM public.ecr.aws/docker/library/python:3.13-slim
RUN apt-get update && apt-get install -y --no-install-recommends ffmpeg \
  && rm -rf /var/lib/apt/lists/*
WORKDIR /srv
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
RUN useradd --create-home app
USER app
```

**Python worker** - a queue consumer that serves no traffic, so it has no health check. Only one
copy may run at a time, so a deploy stops the old container first and gives it 90 seconds to finish
the jobs it holds:

```json modelence.config.json
{
  "$schema": "https://cloud.modelence.com/schema/modelence.config.json?version=1",
  "resources": {
    "worker": {
      "type": "service",
      "dockerfile": "Dockerfile",
      "start": { "commands": ["python -m worker"] },
      "healthCheck": "none",
      "rollout": "replace",
      "stopTimeout": 90
    }
  },
  "env": {
    "REDIS_URL": { "type": "secret" }
  }
}
```

## Setting up a project

These steps are for a Node.js app. For an app in any other language, or one that already builds with
its own Dockerfile, follow [Projects with a Dockerfile](#projects-with-a-dockerfile) instead.

Follow these steps in order. Do not skip the verification step.

1. **Inspect `package.json`.** Read `scripts`, `engines.node`, `type` and the dependencies. Note which
   framework builds the frontend (Vite, Next.js, Create React App, Angular, Astro…) and what runs the
   server (Express, Fastify, Koa, Hono, NestJS, a framework's own server…).

2. **Pick the install command from the lockfile.**
   - `package-lock.json` in sync with `package.json` → `npm ci`. If it is stale or missing, use
     `npm install`.
   - `pnpm-lock.yaml` → `corepack enable && pnpm install --frozen-lockfile`.
   - `yarn.lock` → `corepack enable && yarn install --frozen-lockfile` (Yarn 1) or
     `corepack enable && yarn install --immutable` (Yarn 2+).

   Only npm is preinstalled in the build image; `corepack enable` makes pnpm and Yarn available at the
   version `packageManager` in `package.json` names.

3. **Find the build output.** Vite writes `dist/`, Create React App and Angular write `build/` or
   `dist/<project>/browser`, Astro writes `dist/`, Next.js needs `next build` and its own server
   (`next start`), not a static mount, unless `output: 'export'` is set. Check the framework config for
   a changed `outDir`.

4. **Check the start script.** `vite`, `vite preview`, `react-scripts start`, `next dev`, `nodemon`,
   `ts-node-dev` and `tsx watch` are development servers. Do not use them. Replace them with a
   production start (`node dist/server.js` after a TypeScript build, `next start`, `node server.js`)
   or, for a pure frontend, a static mount and no `start`. Do not add database migrations to
   `start.commands`: every container runs them on every start, several at once during a rollout,
   and a slow one is killed by the health check partway through. Leave migrations out of the file
   and tell the user to run them against the environment's database before deploying. A step may go
   first in `start.commands` only if it is fast and safe to run in parallel, such as `prisma generate`.

5. **Make the server read `PORT`.** The listen call must use `process.env.PORT`, for example
   `app.listen(Number(process.env.PORT) || 3000)`. Bind to all interfaces (the default), not to
   `127.0.0.1` only. If the frontend and the API are served together, the server must be the one
   process — the static mount handles the frontend files, the server handles everything else.

6. **Use the provided databases.** If the project needs MongoDB, read the connection string from
   `process.env.MONGODB_URI` (or `MONGO_URL`) instead of a hardcoded one. If it needs PostgreSQL or
   Redis that it doesn't already have hosted somewhere, declare a managed resource for it in step 7 and
   tie the variable the code reads (`DATABASE_URL`, `REDIS_URL`) to its `url` output. A database hosted
   elsewhere (Supabase, Neon, PlanetScale and so on) works as it is: keep the connection code and read
   its URL and keys from environment variables. Other databases, such as MySQL, are not provisioned. See
   [Compatibility](#when-the-project-is-not-compatible).

7. **Write `modelence.config.json`** at the repository root with the values found above, as a single
   service entry in `resources` (`"type": "service"`). Pick `image` from `engines.node` (default
   `node-22-slim`; use `slim` unless the project already builds on Alpine). Set `root` when the app
   lives in a subdirectory. Add any managed resources from step 6 next to the service, with their
   variables in `env`. Add a `telemetry` resource only when the user asks for traces or metrics, or the
   project already uses OpenTelemetry: a deploy fails on a plan without monitoring. Tie
   `OTEL_EXPORTER_OTLP_ENDPOINT` and `OTEL_EXPORTER_OTLP_HEADERS` to its outputs instead of a hardcoded
   collector. Add `"$schema": "https://cloud.modelence.com/schema/modelence.config.json?version=1"`.

8. **Verify locally.** Run the build commands, then the start commands with `PORT=3000` set, in
   order — exactly as written in the file — and confirm the app answers on
   `http://localhost:3000` (for a static site, confirm the `dir` exists after the build and holds
   `index.html`). Fix the file or the code until this works; a deploy runs the same commands.

9. **Commit `modelence.config.json`** together with any code changes (the `PORT` change, the
   production start script).

10. **Run `npx modelence@latest deploy`** in the project directory yourself, with a timeout of at
    least 15 minutes. It opens the browser, where the user signs in, picks the organization,
    application and environment (or creates a new application or environment there) and enters the
    values of any required variables the environment does not have yet. Tell the user to confirm
    there, then wait for the command to finish: it uploads the project and follows the build until
    the app is live. If you know the target, pass `--app <app> --env <env>` to preselect it; the
    user still confirms it in the browser.

### Runtime values and secrets

When the app needs a value that must not be committed — an API key, an OAuth secret, a third-party
URL — declare it by name in the file's `env` section, without a `value` and with `"type": "secret"`
for anything sensitive. The deploy asks the user for it in the browser; it can be changed later in
the Modelence Cloud dashboard under **Environment variables**. A value only the build needs (a
`VITE_*` or `NEXT_PUBLIC_*` variable that is inlined into the frontend) gets
`"scopes": ["build", "runtime"]`; never give a build scope to anything the browser must not see. Mark
a variable the app runs without `"required": false`. Read the values from `process.env` as usual.

Non-secret settings that belong with the code (a base path, a public API path) go in the file's
`env` section instead, with a `value`, so they are versioned with the repository. Give anything a
bundler inlines `"scopes": ["build", "runtime"]` so it reaches the build as well as the running app.

## Projects with a Dockerfile

Use this path for an app that is not Node.js, such as Python, Go, Ruby, Java, PHP or .NET. Use it
also for a Node.js app that needs system packages the Node.js image doesn't have. The image is built
from the project's Dockerfile, and the platform adds its own entrypoint on top. That entrypoint
loads the environment's variables, runs `start` and passes stop signals to the app. The steps below
keep the image compatible with it. Follow them in order, and do not skip the verification step.

1. **Find or write the Dockerfile.** Use the project's own if it builds a production image;
   otherwise write one. A multi-stage build is fine, and only the final stage runs.

2. **Check the final stage.** It must be based on glibc and have `/bin/sh`, because the platform's
   entrypoint needs both. Debian- and Ubuntu-based images work: `python:3.13-slim`,
   `debian:bookworm-slim`, `ruby:3.3-slim`, `eclipse-temurin:21-jre`. Alpine images (musl) and images
   without a shell (`scratch`, distroless) don't. For a Go or Rust binary, build it in an earlier
   stage and copy it into a `debian:bookworm-slim` final stage. Pull base images through the
   mirror, as in `FROM public.ecr.aws/docker/library/python:3.13-slim`, not from Docker Hub
   (`FROM python:3.13-slim`), which rate-limits the shared build machines.

3. **Move the start command into `start`.** The Dockerfile's `CMD` and `ENTRYPOINT` are not run.
   Put the command that starts the app in `start.commands`, for example `["python -m app"]`. The
   commands run in order under `sh -c`, in the image's `WORKDIR` and as its `USER`, so `$PORT`
   expands. If the image's entrypoint script prepares something before the app starts, run that
   script first in `start`. Keep migrations out of `start`, for the reasons in step 4 of
   [Setting up a project](#setting-up-a-project).

4. **Listen on `PORT`, on all interfaces.** A web server must listen on `0.0.0.0` and the port in
   `PORT`. Many Python servers listen on `127.0.0.1` unless told otherwise, so pass the host:
   `uvicorn app.main:app --host 0.0.0.0 --port $PORT`, or `gunicorn -b 0.0.0.0:$PORT app:app`.
   Development servers, such as `flask run`, `python manage.py runserver` or `uvicorn --reload`,
   must not be used. A process that serves no traffic, such as a queue worker or a bot that holds a
   gateway connection, sets `"healthCheck": "none"` and needs no port.

5. **Pass build-time values.** A build-scoped `env` entry with a `value` in the file reaches the
   build as a build argument: declare it with `ARG NAME` in the stage that uses it. Values set in the
   dashboard are not build arguments, because build arguments are kept in the image's history.
   A `RUN` step reads them from a build secret:

   ```dockerfile
   RUN --mount=type=secret,id=modelence-build-env \
     sh -c 'set -a; . /run/secrets/modelence-build-env; set +a; python scripts/download_model.py'
   ```

   Never write a secret into the image with `ENV`, `ARG` or a file. Variables for the running app
   need nothing in the Dockerfile: they are set when the container starts.

6. **Set how the service is replaced and stopped.** On `SIGTERM` the app should finish its work in
   progress and exit, within `stopTimeout` (30 seconds by default). Set `"rollout": "replace"`
   when two copies must never run at once. A bot that allows one connection is an example, and so
   is a worker that holds state in memory.

7. **Write `modelence.config.json`** with one service entry that sets `dockerfile` (relative to
   `root`) and `start`, as in the [Python examples](#examples). Set `root` to the directory the
   Dockerfile's `COPY` paths are relative to; it is the build context. A `.dockerignore` at `root`
   is used. Add managed resources and `env` as described in step 7 of
   [Setting up a project](#setting-up-a-project), and add `$schema`.

8. **Verify locally** with Docker, from `root`. Replace `<start>` with the `start` commands joined
   with ` && `:

   ```bash
   docker build -f Dockerfile -t modelence-check .
   docker run --rm --entrypoint sh modelence-check -c 'ldd --version'
   docker run --rm -e PORT=3000 -p 3000:3000 --entrypoint sh modelence-check -c '<start>'
   ```

   The second command must print a GNU libc (glibc) version. If it fails, or prints musl, fix step 2.
   For a web service, confirm the app answers on `http://localhost:3000`. For a process with
   `"healthCheck": "none"`, confirm it keeps running. `modelence verify` rehearses Node.js builds
   only, so don't use it for these projects.

9. **Commit and deploy** as in steps 9 and 10 of [Setting up a project](#setting-up-a-project).

### Several services

An environment runs one service. For a project made of several processes, such as an API, a worker
and a bot, deploy each one to its own environment:

- Put a `modelence.config.json` in each service's directory, and run `npx modelence@latest deploy`
  from that directory, choosing that service's environment, or naming it with `--app` and `--env`.
  The CLI remembers the app per directory, in `.modelence/project.json`, but not the environment.
- Only that directory is uploaded, so its Dockerfile can't `COPY` files from outside it. Move
  shared code inside each service's directory, or publish it as a package.
- Services can't reach each other over a private network. They talk through their public URLs, or
  through a queue or database hosted elsewhere, such as Redis, that each environment gets the URL of
  in **Environment variables**. A managed resource belongs to the one environment that declares it.

## When the project is not compatible

Report the project as not compatible with Modelence Cloud, and say why, when:

- **It needs a database other than the provided ones** running alongside it, such as MySQL or
  Elasticsearch. MongoDB, PostgreSQL and Redis are the only databases provisioned.
- **Its processes must reach each other over a private network.** Examples are an app with a
  sidecar, or services that call each other on internal addresses, as Docker Compose sets up. Each
  environment runs one image, and environments can't reach each other privately. Processes that
  talk only through public URLs, or through a queue or database hosted elsewhere, can be deployed as
  [several services](#several-services).
- **Its final image can't be based on glibc with a shell**, for example because it depends on
  Alpine (musl). See step 2 of [Projects with a Dockerfile](#projects-with-a-dockerfile).
- **It needs a GPU.** Containers run on CPUs only.
- **Its image takes more than an hour to build**, which is the build time limit.

A database hosted elsewhere is not a reason to report the project as not compatible. An app that
connects over the network to Supabase, Neon, PlanetScale, a managed Redis or any other hosted
database deploys as usual: keep its connection code, and tell the user to add the URL and keys in the
dashboard under **Environment variables**, marked as secret. A key the frontend bundler inlines, such
as `VITE_SUPABASE_URL`, also needs to be available at build time, as described in
[Runtime values and secrets](#runtime-values-and-secrets).

Then suggest what the user can do instead: replace the database with one that is provided (MongoDB
through `MONGODB_URI`, or a managed PostgreSQL or Redis resource), or keep the incompatible parts on
another host and deploy only the parts that fit.

Do not move a worker, queue consumer or scheduled job into the web process. The web process can run as
several replicas, and each one would run every job — emails sent twice, charges made twice. Deploy
the worker as a service of its own instead, as described in [Several services](#several-services),
with `"healthCheck": "none"`. If the user wants it inside the web process anyway, tell them that
each job needs a lock held in the database, so that only one replica runs it at a time.

## Meteor

<Note>Early support — the commands below work but Meteor is not yet a first-class runtime.</Note>

Meteor bundles its own server; build it into a directory outside the source tree and start the bundle
with Node.js. `ROOT_URL` and `MONGO_URL`, which Meteor reads at start, are already injected. Match
`image` to the Meteor release: Meteor 3 runs on Node 22.

```json modelence.config.json
{
  "$schema": "https://cloud.modelence.com/schema/modelence.config.json?version=1",
  "resources": {
    "app": {
      "type": "service",
      "image": "node-22-slim",
      "build": {
        "commands": [
          "curl https://install.meteor.com/ | sh",
          "meteor npm install",
          "meteor build --directory /tmp/meteor-build --server-only",
          "cd /tmp/meteor-build/bundle/programs/server && npm install"
        ]
      },
      "start": { "commands": ["node /tmp/meteor-build/bundle/main.js"] }
    }
  }
}
```
