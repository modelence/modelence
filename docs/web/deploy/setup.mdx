This page is written for a coding agent. It describes what Modelence Cloud runs, how to choose how
each part of a project is built, and the steps to write and check `modelence.config.json`. If you are
a person, hand it to your agent:

```text
Use https://docs.modelence.com/deploy/setup.md to set up Modelence deployment for this project
```

Read these pages too when the project needs them. Each one is also served as Markdown at its `.md`
URL:

- [modelence.config.json](https://docs.modelence.com/deploy/config.md): every key of the file. Read
  it before writing the file.
- [Dockerfile Services](https://docs.modelence.com/deploy/dockerfile.md): for a service that isn't
  Node.js, or that has its own Dockerfile.
- [Several Services](https://docs.modelence.com/deploy/services.md): for a project with more than one
  process, such as a site and a worker.

## What Modelence Cloud runs

- **One or more services**, each built from the repository into a Docker image and run in containers
  of its own. A service is built one of two ways:
  - **Node.js**: on an official Node.js image, 18 or newer, with the `build` commands, and started
    with the `start` commands. Only npm is preinstalled. Optional `static` directories are served in
    front of the process by the platform.
  - **Dockerfile**: from the project's own Dockerfile, in any language.
- **One public service** that gets the environment's URL. Other services are private: only the
  environment's own services reach them.
- **Optional managed PostgreSQL databases and Redis caches**, declared in `resources` next to the
  services. A deploy creates each one, and the app gets its connection details through the variables
  `env` ties to it. They need a paid plan.
- **Optional telemetry**, a `resources` entry of type `"telemetry"`, for the app's traces and metrics.
  It needs a plan with monitoring (Pro and up). Logs need no setup.
- **Environment variables injected at start**, in every service:
  - `MONGODB_URI` and `MONGO_URL`: a MongoDB Atlas database provisioned for this environment.
  - `SITE_URL` and `ROOT_URL`: the environment's public URL.
  - `PORT`: the port the process must listen on. A hardcoded port never receives traffic.
  - The variables the user defines in the dashboard, and the ones `env` ties to a resource.

Containers have no persistent disk: each deploy replaces them, and files written to disk are lost.

## Choose how each service is built

Decide this for every process the project runs in production:

- **A Node.js app** is a Node.js service. Use the examples below.
- **An app in another language** (Python, Go, Ruby, Java, Rust, PHP, .NET…), **or a Node.js app that
  needs system packages** (`ffmpeg`, Chromium, native libraries), is a Dockerfile service. Use the
  project's Dockerfile if it has one that works, or write one. Follow
  [Dockerfile Services](/deploy/dockerfile).
- **More than one process**, such as a site and a background worker, or a frontend and an API in
  another language, is several services. Follow [Several Services](/deploy/services). More than one
  service needs a paid plan: tell the user.

A `docker-compose.yml` is not read, but it shows the processes. Each entry built from the repository
(`build:`) becomes a service. A `postgres`, `redis` or `mongo` image becomes a provided database. A
`Procfile` lists processes the same way: `web` is the public service, and the others are private
services.

## Node.js examples

**Express API only**: no build step, the server serves everything:

```json modelence.config.json
{
  "$schema": "https://cloud.modelence.com/schema/modelence.config.json?version=1",
  "resources": {
    "api": {
      "type": "service",
      "image": "node-22-slim",
      "build": { "commands": ["npm ci"] },
      "start": { "commands": ["node server.js"] }
    }
  }
}
```

**Vite static site**: built once, served by the platform, no process:

```json modelence.config.json
{
  "$schema": "https://cloud.modelence.com/schema/modelence.config.json?version=1",
  "resources": {
    "web": {
      "type": "service",
      "image": "node-22-slim",
      "build": { "commands": ["npm ci", "npm run build"] },
      "static": [{ "path": "/", "dir": "dist" }]
    }
  }
}
```

**Express API + Vite frontend**: the frontend in `client/` is built into `client/dist` and served at
`/`; requests that match no file reach the API. `VITE_API_URL` is scoped to the build as well because
Vite inlines it while building:

```json modelence.config.json
{
  "$schema": "https://cloud.modelence.com/schema/modelence.config.json?version=1",
  "resources": {
    "api": {
      "type": "service",
      "image": "node-22-slim",
      "build": {
        "commands": ["npm ci", "npm ci --prefix client", "npm run build --prefix client"]
      },
      "start": { "commands": ["node server.js"] },
      "static": [{ "path": "/", "dir": "client/dist" }]
    }
  },
  "env": {
    "VITE_API_URL": { "value": "/api", "scopes": ["build", "runtime"] },
    "STRIPE_SECRET_KEY": { "type": "secret" }
  }
}
```

**Express API with PostgreSQL and Redis**: the deploy creates the database and the cache, and the
app reads them from `DATABASE_URL` and `REDIS_URL`:

```json modelence.config.json
{
  "$schema": "https://cloud.modelence.com/schema/modelence.config.json?version=1",
  "resources": {
    "api": {
      "type": "service",
      "image": "node-22-slim",
      "build": { "commands": ["npm ci"] },
      "start": { "commands": ["node server.js"] }
    },
    "main-db": { "type": "postgres", "plan": "postgres-1gb" },
    "cache": { "type": "redis" }
  },
  "env": {
    "DATABASE_URL": { "type": "resource", "resource": "main-db", "output": "url" },
    "REDIS_URL": { "type": "resource", "resource": "cache", "output": "url" }
  }
}
```

**Express API with telemetry**: the OpenTelemetry SDK reads the two variables, so requests and
database calls reach the environment without code changes. Logs are already collected from the app's
output, so `OTEL_LOGS_EXPORTER` turns off the SDK's own log export. The project depends on
`@opentelemetry/auto-instrumentations-node`, which `--require` loads before the server:

```json modelence.config.json
{
  "$schema": "https://cloud.modelence.com/schema/modelence.config.json?version=1",
  "resources": {
    "api": {
      "type": "service",
      "image": "node-22-slim",
      "build": { "commands": ["npm ci"] },
      "start": {
        "commands": ["node --require @opentelemetry/auto-instrumentations-node/register server.js"]
      }
    },
    "otel": { "type": "telemetry" }
  },
  "env": {
    "OTEL_EXPORTER_OTLP_ENDPOINT": { "type": "resource", "resource": "otel", "output": "endpoint" },
    "OTEL_EXPORTER_OTLP_HEADERS": { "type": "resource", "resource": "otel", "output": "headers" },
    "OTEL_SERVICE_NAME": { "value": "api" },
    "OTEL_LOGS_EXPORTER": { "value": "none" }
  }
}
```

Examples in other languages are on [Dockerfile Services](/deploy/dockerfile), and examples with
several services are on [Several Services](/deploy/services).

## Setting up a project

Follow these steps in order. Do not skip the verification step.

1. **Inspect the project.** Find its languages and package managers (`package.json`,
   `pyproject.toml`, `requirements.txt`, `go.mod`, `Gemfile`, `pom.xml`…), any `Dockerfile`,
   `docker-compose.yml` or `Procfile`, and how a monorepo is laid out. List the processes it runs in
   production: the web server, and any worker, scheduler or second API.

2. **Choose how each process is built**, as described in
   [Choose how each service is built](#choose-how-each-service-is-built). Name each service after what
   it does (`web`, `api`, `worker`).

3. **For each Node.js service:**
   - **Pick the install command from the lockfile.** `package-lock.json` in sync with
     `package.json` → `npm ci`; if it is stale or missing, `npm install`. `pnpm-lock.yaml` →
     `corepack enable && pnpm install --frozen-lockfile`. `yarn.lock` →
     `corepack enable && yarn install --frozen-lockfile` (Yarn 1) or
     `corepack enable && yarn install --immutable` (Yarn 2+). `corepack enable` makes pnpm and Yarn
     available at the version `packageManager` in `package.json` names.
   - **Find the build output.** Vite writes `dist/`, Create React App and Angular write `build/` or
     `dist/<project>/browser`, Astro writes `dist/`. Next.js needs `next build` and its own server
     (`next start`), not a static mount, unless `output: 'export'` is set. Check the framework config
     for a changed `outDir`.
   - **Check the start script.** `vite`, `vite preview`, `react-scripts start`, `next dev`,
     `nodemon`, `ts-node-dev` and `tsx watch` are development servers. Do not use them. Replace them
     with a production start (`node dist/server.js` after a TypeScript build, `next start`,
     `node server.js`) or, for a pure frontend, a static mount and no `start`.
   - **Make the server read `PORT`**, for example `app.listen(Number(process.env.PORT) || 3000)`.
     Bind to all interfaces (the default), not to `127.0.0.1` only. If the frontend and the API are
     served together, the server must be the one process: the static mount handles the frontend
     files, the server handles everything else.
   - **Pick `image`** from `engines.node` (default `node-22-slim`; use `slim` unless the project
     already builds on Alpine), and set `root` when the app lives in a subdirectory.

4. **For each Dockerfile service**, follow [Dockerfile Services](/deploy/dockerfile): use or write
   the Dockerfile, make the process listen on `0.0.0.0`, and set `port` when it listens on a fixed
   port other than 3000.

5. **Don't run migrations at start.** Do not add database migrations to `start` or to a Dockerfile's
   `CMD`: every container runs them on every start, several at once during a rollout, and a slow one
   is killed by the health check partway through. Leave them out and tell the user to run them against
   the environment's database before deploying. A step may run before the server only if it is fast
   and safe to run in parallel, such as `prisma generate`.

6. **Use the provided databases.** If the project needs MongoDB, read the connection string from
   the `MONGODB_URI` (or `MONGO_URL`) variable instead of a hardcoded one. If it needs PostgreSQL or
   Redis that it doesn't already have hosted somewhere, declare a managed resource for it in step 7
   and tie the variable the code reads (`DATABASE_URL`, `REDIS_URL`) to its `url` output. A database
   hosted elsewhere (Supabase, Neon, PlanetScale and so on) works as it is: keep the connection code
   and read its URL and keys from environment variables. Other databases, such as MySQL, are not
   provisioned. See [Compatibility](#when-the-project-is-not-compatible).

7. **Write `modelence.config.json`** at the repository root, with one entry in `resources` for each
   service (`"type": "service"`), as described in [modelence.config.json](/deploy/config).
   - Add any managed resources from step 6 next to the services, with their variables in `env`.
   - With several services, set `"public": true` on the one that serves the site, and give each
     service that calls another a `"type": "resource"` variable with the other's `url`. See
     [Several Services](/deploy/services).
   - Add a `telemetry` resource only when the user asks for traces or metrics, or the project already
     uses OpenTelemetry: a deploy fails on a plan without monitoring. Tie
     `OTEL_EXPORTER_OTLP_ENDPOINT` and `OTEL_EXPORTER_OTLP_HEADERS` to its outputs instead of a
     hardcoded collector.
   - Add `"$schema": "https://cloud.modelence.com/schema/modelence.config.json?version=1"`.

8. **Verify locally**, each service on its own:
   - A Node.js service: run its build commands, then its start commands with `PORT=3000` set, in
     order and exactly as written in the file, and confirm the app answers on
     `http://localhost:3000`. For a static site, confirm the `dir` exists after the build and holds
     `index.html`.
   - A Dockerfile service: build and run its image as described in
     [Verifying the build](/deploy/dockerfile#verifying-the-build).

   Fix the file or the code until this works; a deploy runs the same build.

9. **Commit `modelence.config.json`** together with any code changes (the `PORT` change, the
   production start script, a new Dockerfile).

10. **Run `npx modelence@latest deploy`** in the project directory yourself, with a timeout of at
    least 15 minutes. It opens the browser, where the user signs in, picks the organization,
    application and environment (or creates a new application or environment there) and enters the
    values of any required variables the environment does not have yet. Tell the user to confirm
    there, then wait for the command to finish: it uploads the project and follows the build until
    the app is live. If you know the target, pass `--app <app> --env <env>` to preselect it; the
    user still confirms it in the browser.

### Runtime values and secrets

When the app needs a value that must not be committed (an API key, an OAuth secret, a third-party
URL), declare it by name in the file's `env` section, without a `value` and with `"type": "secret"`
for anything sensitive. The deploy asks the user for it in the browser; it can be changed later in
the Modelence Cloud dashboard under **Environment variables**. A value only the build needs (a
`VITE_*` or `NEXT_PUBLIC_*` variable that is inlined into the frontend) gets
`"scopes": ["build", "runtime"]`; never give a build scope to anything the browser must not see. Mark
a variable the app runs without `"required": false`. Read the values from the environment as usual
(`process.env`, `os.environ`, `os.Getenv`). A Dockerfile reads build variables in its own way; see
[Variables in the build](/deploy/dockerfile#variables-in-the-build).

Non-secret settings that belong with the code (a base path, a public API path) go in the file's
`env` section instead, with a `value`, so they are versioned with the repository. Give anything a
bundler inlines `"scopes": ["build", "runtime"]` so it reaches the build as well as the running app.

## When the project is not compatible

Report the project as not compatible with Modelence Cloud, and say why, when:

- **It needs a database or another stateful server that isn't provided** and that the user doesn't
  host elsewhere: MySQL, Elasticsearch, RabbitMQ and so on. MongoDB, PostgreSQL and Redis are the only
  ones provisioned, and a service can't run one itself, since containers have no persistent disk.
- **It keeps data on the local disk**: a SQLite file, or uploads written to a folder. Each deploy
  replaces the containers and loses those files. Suggest PostgreSQL or MongoDB for the data, and an
  external storage service for files.
- **It needs more than 5 services.**

A database hosted elsewhere is not a reason to report the project as not compatible. An app that
connects over the network to Supabase, Neon, PlanetScale, a managed Redis or any other hosted
database deploys as usual: keep its connection code, and tell the user to add the URL and keys in the
dashboard under **Environment variables**, marked as secret. A key the frontend bundler inlines, such
as `VITE_SUPABASE_URL`, also needs to be available at build time, as described in
[Runtime values and secrets](#runtime-values-and-secrets).

Then suggest what the user can do instead: replace the database with one that is provided (MongoDB
through `MONGODB_URI`, or a managed PostgreSQL or Redis resource), or keep the incompatible parts on
another host and deploy the rest.

Do not move a worker, queue consumer or scheduled job into the web process. The web process can run as
several replicas, and each one would run every job: emails sent twice, charges made twice. Run it as
a service of its own, as described in [Several Services](/deploy/services#examples).

## Meteor

<Note>Early support: the commands below work but Meteor is not yet a first-class runtime.</Note>

Meteor bundles its own server; build it into a directory outside the source tree and start the bundle
with Node.js. `ROOT_URL` and `MONGO_URL`, which Meteor reads at start, are already injected. Match
`image` to the Meteor release: Meteor 3 runs on Node 22.

```json modelence.config.json
{
  "$schema": "https://cloud.modelence.com/schema/modelence.config.json?version=1",
  "resources": {
    "app": {
      "type": "service",
      "image": "node-22-slim",
      "build": {
        "commands": [
          "curl https://install.meteor.com/ | sh",
          "meteor npm install",
          "meteor build --directory /tmp/meteor-build --server-only",
          "cd /tmp/meteor-build/bundle/programs/server && npm install"
        ]
      },
      "start": { "commands": ["node /tmp/meteor-build/bundle/main.js"] }
    }
  }
}
```
